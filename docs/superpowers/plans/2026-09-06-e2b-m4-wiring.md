**Tech Stack:** CPython 3.14 + ctypes FFI（fork wheel `sandlock 0.9.0-beta`，`SandboxInstance`/`ExecProcess`/`ExecStdio`）、FastAPI worker/control plane、pytest（unit/contract/security/sdk）、multinode harness。

## 3. 关键决策（结论 + 理由 + 证据）

### D1 实例生命周期：启动时机、关闭路径清单、幂等与异常

**结论：惰性启动（首次 `executor.start()`/网关启动时建箱）+ 实例 closed/dead 时"重建一次并重试"；显式关闭只发生在一个收口点（ctx.shutdown/卸载），其余控制面路径全部最终汇到它。**

理由与证据：
- file-only 沙箱（大量文件 API、零命令、无 MCP）不应占用实例与 24 h 时钟；`SandboxRuntimeContext` 在首次 RPC 才被创建（`envd_service/rpc.py:33-35`），实例再进一步惰性到首次 `start()`（executor 是 context 单例，`context.py:74-76`）。
- fork 实例自带 idle 15 min / 24 h 上限（instance.rs:186-228；FFI launch 无 lifetime 覆盖，lib.rs:3227-3231）——E2B 无法关闭 idle，**必须**把 "closed/Dead → 重建一次"当一等语义，否则 24 h 后全沙箱静默坏掉。重建仅发生在"child 表空/无 waiter"的 closed 情形（idle 回收），不会撕裂在跑 child；Dead（listener/channel 故障）时 child 已不可靠，重建前先按 ctx.shutdown 路径收尸再重启实例，并向 SDK 命令报 500 级错误（不伪装 127）。
- E2B 关闭路径清单（全部最终触发 `SandboxInstance.close()`）：
  1. `DELETE /sandboxes/{id}` / evict kill / orphan reconcile：`runtime_registry.unregister` → `create_app` 注册的 unregister 回调 `runtimes.pop(...).shutdown()`（`envd_service/app.py:231-236`）→ `ctx.shutdown()`（context.py:148）→ 新增 `executor.close()`；
  2. 远程 worker：`/agent/sandboxes/{id}` delete → 同 worker 侧 unregister 回调链（`envd_service/agent.py:160-212` + app.py 同一注册）；

### D2 实例身份：name 传什么、目录/token 归属、同 id 冲突

**结论：`name=sandbox_id`；目录与 token 全由 fork 完成，E2B 零接触；同 id 冲突 = fork 拒绝（live/ambiguous），E2B 映射为明确 500 级错误并保留现场（绝不 remove_dir_all 或抢占）。**

理由与证据：
- fork 已把"名字 = 身份"做成"目录名哈希 + token 文件 + starttime 证伪 + 冲突拒绝"（control.rs:1-158、264-458）；§7.2 第 6 点的 E2B 需求（目录名用 sandbox_id+token）已由 fork 侧 F1.3 以更强形态交付 ⇒ **E2B 无需再造**。
- sandbox_id 生成形态 `sbx_` + 16 hex = 20 字节（`gateway_common/ids.py`），远小于 fork 64 字节上限（sandbox.py:676-691 校验 `len(name.encode()) > 64`）；用户自定义 id 允许 1–128（`gateway_common/paths.py` `_SANDBOX_ID_RE`），>64 字节时 Python 显式 name 参数不经该校验（FFI `optional_name` 只查 UTF-8，lib.rs:3623-3631）⇒ E2B 侧派生稳定名：`sbx_<sha256(sandbox_id).hexdigest()[:16]>`（E2B 内维护 `sandbox_id → instance_name` 映射供日志）。
- 冲突语义：同名 launch 遇 Live/Ambiguous 一律 `AlreadyExists` 拒绝（control.rs:410-458）；仅"pid 文件三行齐全且 starttime 不匹配"判 Stale 才回收。多 worker 同 id 双活只在控制面路由错误时发生；E2B 把它当"worker 状态与事实不符"的硬错误（500 + 日志点名 sandbox_id 与 PID），不做静默抢活。

### D3 gateway+命令同实例：executor.start() 单实例化、MCP 端口 ceiling、PTY、per-exec 映射、127 语义

**结论：**
1. `SandlockExecutor` 增加 `_instance` 槽 + `_ensure_instance()`；`start()` 与 `ctx.start_mcp_gateway()` 都经 `_ensure_instance()` 后 `exec()`。
2. 实例 ceiling 拆出"与命令无关"的策略；MCP host 端口在 `SandboxRuntimeContext.__init__`（record.mcp 存在时）预分配并 `executor.set_mcp_bind_port(port)`，ceiling `net_allow_bind=[port]`；网关 exec 传 `bind_ports=[port]`；命令 exec 不传。已知边界：FUP-19 记"per-child 正向 bind/fs 收窄非内核强制"（instance.rs Landlock 域共享），因此命令理论上仍可 bind 该端口，但只有唯一已知端口、且网关先绑定（EADDRINUSE），风险记入 release note/security 注记，不在本期引入 fork 中介层。

5. 127 语义：沙箱内 `execvp` 失败由 init `_exit(127)`（init/mod.rs:217-227）→ `wait()` 得 exit_code 127，走既有 SDK 报错链；不再依赖 `FileNotFoundError` catch。实例级失败（closed/policy/launch）与 127 分开：manager 现有 `except Exception → FailedRunningProcess`（manager.py:307-314）只保留给真正的 exec 通道失败；closed 重建逻辑在 executor 内先消化（D1）。
6. `resolve_cmd`、网关 `python3 mcp-gateway` 显式解释器形态保持不变（沙箱内 exec ELF-only 约束仍在）。

### D5 pause/resume：实例无 freeze/thaw 时的最小可行方案

**结论：不做 fork 改动即可保持现有语义——pause/resume 继续由 worker 直发 `os.killpg(os.getpgid(child_pid), SIGSTOP/SIGCONT)`。** 依据：
- F1.7 起每个 confined child 自带进程组（init/mod.rs:12-26、138-153；instance.rs:2640-2668 注释"pid==pgid under per-child-group layout"），exec child 的 host pid 就是组首；
- core `kill_child` 的注册表路径也是 group-first killpg + pidfd 补刀（instance.rs:2646-2668），与 worker 直发同构；
- "能不能 SIGSTOP init/网关"：不能/不需要——init 不是注册 child；网关若要暂停需它的 child group（网关自身是 child，可被 killpg 命中）。现有 E2B 语义 pause 只暂停命令树（manager.py:473-501），网关不在 `ProcessManager`（context.py:167 直接 executor.start）⇒ 维持"pause 不停网关"现状，把该语义写进文档（MCP 请求在 paused 态仍可达属既有行为，不是 M4 引入）。
- Python `ExecProcess.kill()` 硬编码 SIGKILL（sandbox.py:2269-2287）不阻塞本方案；若未来要"经注册表投任意信号"（pidfd 补刀逃逸 setsid 进程），fork 最小 API = Python `ExecProcess.kill(sig: int = signal.SIGKILL)` 放开 signum 透传（FFI 已支持），标 ⚠️ 见文末，本期不强制。
- 约束核对：worker euid 与 child 同 uid（非 root worker 固定身份档）或 worker 为 root（per-sandbox-uid 档）时 killpg 才有权限——与现状完全一致，无新增风险；pause 后 SIGKILL 清理由 `kill_all` 仍可命中（SIGSTOP 进程可收 SIGKILL）。
